# Domain Model Document

## 1. Purpose
This document defines the canonical domain model for the AI Home Designer. It translates the approved product requirements and system architecture into stable domain concepts, relationships, invariants, value objects, lifecycle rules, validation boundaries, and persistence expectations.

The domain model is the contract shared by:
*   the web application
*   the API/application services
*   the deterministic design engine
*   plan analysis
*   the 2D editor
*   the 3D renderer
*   walkthrough generation
*   versioning
*   client review
*   export

The domain model does not depend on React, Express, Prisma, Gemini, Three.js, browser APIs, or cloud vendors.

## 2. Domain Authority Rules

### 2.1 Canonical design authority
`HouseDesign` is the only authoritative representation of residential design geometry.

The following are derived views and must never become parallel authoritative models:
*   SVG 2D rendering
*   3D scene graph
*   walkthrough collision/navigation structures
*   analysis visualizations
*   export rendering

### 2.2 AI authority boundary
AI may create or modify structured intent, preferences, and explanations through approved application commands. AI may not directly own or persist authoritative geometry.

### 2.3 Server authority
Tenant ownership, project access, version access, and share-link permissions are application/security concerns enforced by the server. UI state is never an authorization source.

### 2.4 Immutable version authority
A saved `DesignVersion` is immutable. The active design draft is mutable and carries optimistic-concurrency metadata.

## 4. Identity and Identifier Rules
All persisted entities use opaque identifiers. UUIDs are appropriate for MVP.

**Rules:**
*   IDs are generated by the application/domain boundary, not by the browser.
*   IDs are never reused.
*   Public URLs must not expose sequential database IDs where avoidable.
*   Child objects inside `HouseDesign` also have stable IDs.
*   A stable object ID survives ordinary edits and is replaced only when the domain intentionally replaces the object.
*   External provider IDs are not used as domain primary keys.

**Recommended naming:**
*   `ProjectId`
*   `PlotId`
*   `HouseDesignId`
*   `RoomId`
*   `WallId`
*   `DesignVersionId`
*   `ShareLinkId`

## 5. Units and Coordinate System

### 5.1 Canonical unit
The domain stores dimensions in millimetres as the canonical linear unit.

**Rationale:**
*   suitable for residential planning precision
*   avoids floating ambiguity caused by mixed centimetre/feet representations
*   easy to convert to display units

User-facing units may include metric or imperial display settings, but persistence remains canonical.

### 5.2 Coordinate system
MVP uses a right-handed 2D plan coordinate system:
*   `x` increases east/right on the plan
*   `y` increases north/up on the plan
*   coordinates are relative to the project plot origin
*   geometric calculations use the canonical millimetre unit

A separate 3D projection maps the 2D plan into world coordinates. The 3D scene must not redefine canonical geometry.

### 5.3 Angles
Angles are stored in degrees at the domain boundary and converted to radians only in math/rendering adapters where required.

### 5.4 Numerical tolerance
Geometry comparisons use an explicit domain tolerance instead of direct floating-point equality. The tolerance is centralized in the `design-engine`/domain math utilities.

## 6. Aggregate Boundaries
The principal aggregates are:

*   **Workspace aggregate:** Owns tenant-level membership and workspace settings.
*   **Project aggregate:** Owns project lifecycle, plot/site context, user requirements, design intent metadata, and references to design drafts/versions.
*   **HouseDesign aggregate:** Owns all canonical residential geometry and design-specific constraints/preferences.
*   **DesignVersion aggregate:** Owns one immutable complete snapshot of a `HouseDesign` and version metadata.
*   **ClientReview aggregate:** Owns review access, review state, comments, approval state, and associated scoped share links.

The API/application layer is responsible for composing data across aggregates. Domain objects do not perform database queries.

## 7. Workspace and Access Model

### 7.1 Workspace
A workspace represents either:
*   a personal homeowner workspace
*   a company/professional workspace

**Conceptual fields:**
```typescript
interface Workspace {

  type: 'PERSONAL' | 'COMPANY';
  name: string;
  createdAt: Date;
  updatedAt: Date;

```

### 7.2 Workspace membership
```typescript
interface WorkspaceMember {
  workspaceId: string;
  userId: string;

  createdAt: Date;
```

The exact UI role names may map to the product roles Administrator and Team Member without changing domain authorization semantics.

### 7.3 Tenant ownership invariant
Every project belongs to exactly one workspace. Every workspace-owned child resource is reachable only through a project/workspace relationship that passes server-side authorization.

The project is the container for one residential planning engagement.

**Conceptual structure:**
```typescript
interface Project {

  name: string;
  status: 'DRAFT' | 'ACTIVE' | 'ARCHIVED';
  clientName?: string;
  address?: string;
  createdBy: string;
  createdAt: Date;
  updatedAt: Date;
  archivedAt?: Date;

```

### 8.2 Project status
*   `DRAFT`
*   `ACTIVE`
*   `ARCHIVED`

### 8.3 Project lifecycle
Created → Plot/Site Setup → Requirements → Design Brief → Concept Generation → Analysis / Editing → Versioning → 3D / Walkthrough → Client Review → Export → Archived (optional)

The lifecycle is workflow guidance rather than an artificial restriction preventing legitimate editing earlier in the process.

## 9. Plot and Site Model

### 9.1 Plot
Plot represents the land parcel available for planning.

**Conceptual fields:**
```typescript
interface Plot {
  id: string;
  projectId: string;
  boundary: Polygon;
  area: number;
  frontage: number;
  depth: number;
  shapeType: string;
  buildableBoundary?: Polygon;
  setbacks: Setbacks;
}
```

### 9.2 Plot boundary
MVP supports orthogonal/standard polygon boundaries required by the approved requirements. Non-orthogonal and complex curved geometry is a controlled future capability unless explicitly enabled.

### 9.3 Setbacks
```typescript
interface Setbacks {
  front: number;
  rear: number;
  left: number;
  right: number;
}
```
Values are stored in millimetres.

### 9.4 Buildable area
The deterministic engine derives the effective buildable area from the plot boundary and applicable setbacks/constraints. The derived buildable region is not an independently edited source of truth.

### 9.5 Site
Site captures context that affects planning without claiming legal survey authority.

**Conceptual fields:**
```typescript
interface Site {
  accessPoints: Point[];
  roadEdges: Line[];
  neighboringContext: ContextInfo[];
  siteImages: Asset[];
  northDirection: number;
  slope?: number;
  notes?: string;
  surveyConfidence?: number;
}
```
Photo/survey analysis is assistive and may carry confidence metadata rather than asserting legal measurements.

### 10.2 Requirement categories

*   floor count
*   room count
*   room sizes
*   parking
*   kitchen type
*   bathroom count
*   staircase requirement
*   future expansion
*   natural-light preference
*   privacy
*   budget-related planning preference
*   Vastu preference

### 10.3 Requirement priority
*   `MUST`
*   `SHOULD`
*   `NICE_TO_HAVE`

These priorities influence conversion into hard constraints and soft preferences but do not alone determine validity.

## 11. DesignIntent Model
DesignIntent is the validated normalized interpretation of requirements used by the deterministic engine.

**Conceptual structure:**
```typescript
interface DesignIntent {
  schemaVersion: string;
  projectId: string;
  plotContext: PlotContext;
  floorsRequested: number;
  rooms: RoomIntent[];
  circulationRequirements: CirculationIntent;
  staircaseRequirements: StaircaseIntent;
  parkingRequirements: ParkingIntent;
  daylightPreferences: DaylightPreference;
  privacyPreferences: PrivacyPreference;
  vastuPreferences: VastuPreference;
  futureExpansionPreferences: FutureExpansionPreference;
  hardConstraints: HardConstraint[];
  softPreferences: SoftPreference[];
  unresolvedQuestions: Question[];
  sourceRequirementIds: string[];
}
```

### 11.1 AI-created intent
AI may create a candidate `DesignIntent`, but application validation must normalize it before the design engine consumes it.

### 11.2 Impossible/ambiguous intent
An unresolved or contradictory intent must be represented explicitly, for example:
*   `unresolvedQuestions[]`
*   `conflicts[]`

The system must not invent hidden assumptions and silently continue with a materially different design intent.

## 12. Design Constraints and Preferences

### 12.1 Hard constraints
Hard constraints are mandatory domain rules such as:
*   geometry must remain within the permitted buildable region
*   rooms must meet configured minimum dimensions where such a requirement exists
*   walls must not create invalid self-intersections
*   required rooms must exist
*   required access/circulation rules must be satisfied
*   doors/windows/stairs must occupy valid geometry
*   required structural planning placeholders must be valid according to the product's conceptual rules

Hard constraints are binary for validation: violated or satisfied.

### 12.2 Soft preferences
Soft preferences are scored or classified separately and must never be mislabeled as hard validity rules.

**Examples:**
*   Vastu preference
*   preferred orientation
*   preferred room adjacency
*   daylight preference
*   privacy preference
*   view preference
*   future expansion preference

### 12.3 Vastu
Vastu is represented as a configurable traditional preference system. It may produce:
*   satisfied preference
*   partially satisfied preference
*   unsatisfied preference
*   informational warning

It is not a scientific or structural validity mechanism.

## 14. Geometry and Topology Invariants
The following invariants must hold for a valid `HouseDesign`:
*   All referenced floors exist.
*   All referenced walls, rooms, doors, windows, and stairs exist before they are referenced.
*   Coordinates are finite numbers within safe domain bounds.
*   Wall segments have non-zero length.
*   Wall thickness is positive.
*   Room geometry is valid and non-degenerate.
*   Invalid room overlaps are rejected.
*   Wall intersections are represented deterministically.
*   Doors and windows reference valid host walls.
*   Door/window extents fit within the host wall's supported opening region.
*   Staircases reference valid source/destination floors where multi-floor stairs are used.
*   Furniture has valid dimensions and finite transforms.
*   All design geometry satisfies plot/buildable-area constraints unless a clearly modeled exception exists.
*   No NaN or infinite geometry reaches persistence or rendering.
*   Units and schema versions are explicit.

The domain may use repair/normalization helpers for deterministic arithmetic corrections, but silent semantic changes to user intent are prohibited.

## 17. Concept Generation Model
A concept is a fully validated candidate `HouseDesign` produced from one validated `DesignIntent`.

**Concept generation:**
Validated DesignIntent → Constraint compilation → Deterministic layout search → Candidate generation → Hard validation → Soft preference evaluation → De-duplication / diversity check → Up to 5 valid concepts

### 17.1 Determinism
The engine should support a fixed seed for reproducible tests and debugging.

### 17.2 Diversity
The engine must not return the same geometry repeatedly under different concept IDs. Diversity should be represented through meaningful deterministic strategy variation such as:
*   room ordering
*   circulation strategy
*   adjacency priority ordering
*   orientation preference trade-offs
*   placement heuristics

### 17.3 Fewer than 5 concepts
Five is the target, not an absolute guarantee. If fewer valid concepts exist, the result includes the valid concepts plus a structured explanation of why additional concepts could not be produced.

## 18. Design Analysis Model
Analysis is derived from a validated `HouseDesign` and must not mutate geometry.

**Analysis findings may include:**
*   room areas
*   dimension checks
*   circulation findings
*   room adjacency observations
*   entry/egress observations
*   opening placement checks
*   buildable-area compliance
*   soft preference results
*   Vastu preference findings
*   daylight/sunlight findings where supported
*   warnings and informational notes

**Conceptual structure:**
```typescript
interface DesignAnalysis {
  designVersionOrRevision: string;
  generatedAt: Date;
  summary: string;
  findings: Finding[];
}

interface Finding {
  code: string;
  severity: 'ERROR' | 'WARNING' | 'INFO';
  category: string;
  message: string;
  relatedEntityIds: string[];
  evidence: any;
}
```
Analysis must clearly distinguish hard-invalid conditions from preference or informational findings.

## 19. Active Draft, Autosave, and Concurrency

### 19.1 Active draft
Only one authoritative active draft exists for the current project design state unless an explicit future collaboration model is introduced.

### 19.2 Draft revision
Every persisted active-draft mutation increments a revision number. Write requests include the expected revision: `expectedRevision == currentRevision`

If they differ, the server returns a concurrency conflict and does not silently overwrite newer state.

### 19.3 Autosave
The client may debounce saves for usability, but the server treats each save as a validated command. Debouncing is not an authorization or integrity mechanism.

### 19.4 Conflict handling
MVP uses optimistic concurrency. Future real-time collaborative editing may introduce operational transforms or CRDTs, but those are explicitly out of MVP scope.

## 20. DesignVersion Model
A `DesignVersion` is an immutable snapshot of the canonical design.

**Conceptual fields:**
```typescript
interface DesignVersion {
  id: string;
  projectId: string;
  sourceDraftRevision: number;
  versionNumber: number;
  label?: string;
  snapshot: any;
  createdBy: string;
  createdAt: Date;
  metadata: any;
}
```

### 20.1 Snapshot rule
The snapshot must be self-contained enough to reproduce the exact canonical design state that was reviewed/exported.

### 20.2 Restore
Restoring a version does not mutate the historical version. It creates a new active draft state derived from that snapshot.

### 20.3 Comparison
Version comparison is computed between snapshots and produces a derived diff. Historical snapshots remain unchanged.

## 22. Persistence Mapping
The domain model and database model are related but not identical.

**Recommended persistence strategy:**
*   relational tables for tenant/project/access/version metadata
*   relational tables for frequently queried top-level design entities where useful
*   JSONB snapshot for immutable `DesignVersion` payloads
*   JSONB or normalized representation for active draft geometry depending on measured query requirements

The persistence layer maps database records to domain structures. Prisma models must not be returned directly from API handlers.

### 22.1 Transaction boundaries
Transactions are required for operations that must be atomic, such as:
*   saving a version and updating project/version metadata
*   restoring a version into the active draft
*   revoking a share link and updating associated review state when applicable
*   updating multiple tightly coupled draft records where partial persistence would create invalid state

## 23. Serialization and Schema Versioning
Every serialized `HouseDesign` and `DesignVersion` includes `schemaVersion`.

**Rules:**
*   Schema changes must be explicit.
*   Old versions remain readable for as long as supported by the product.
*   Migrations must be deterministic and tested.
*   New application code must not silently reinterpret old geometry with changed semantics.
*   Unsupported schema versions fail clearly rather than being guessed.

## 24. Derived Representations

### 24.1 2D projection
HouseDesign → 2D projection adapter → SVG render tree

The SVG node IDs map back to canonical domain object IDs.

### 24.2 3D projection
HouseDesign → 3D geometry builder → Three.js / React Three Fiber scene

Wall meshes, floors, openings, stairs, and furniture are generated from canonical objects.

### 24.3 Walkthrough projection
HouseDesign → 3D scene + navigable-space derivation → Camera + collision/navigation runtime

Navigation data is cached/derived runtime state, not a new authoritative design model.

## 26. Domain Invariants Summary
The following invariants are mandatory:
*   A project belongs to one workspace.
*   A design belongs to one project.
*   A saved version belongs to one project and references a complete snapshot.
*   Historical versions are immutable.
*   Active draft edits use optimistic concurrency.
*   Geometry uses canonical units and coordinate rules.
*   Invalid geometry cannot become authoritative state.
*   AI output cannot bypass deterministic validation.
*   Hard constraints are separate from soft preferences.
*   Vastu is a preference system, not a scientific validity rule.
*   Doors/windows reference valid walls.
*   Staircases reference valid floors.
*   Renderers consume canonical state rather than creating parallel authority.
*   Analysis does not mutate design geometry.
*   Share links cannot expand beyond their explicit scopes.
*   Share-link secrets are never persisted in plaintext.
*   No entity may contain NaN, infinite coordinates, or unsupported schema versions.
*   Tenant authorization is enforced outside the domain by application/security boundaries, never assumed from client input.

## 27. Testing Strategy for the Domain Model
Domain tests should be deterministic and framework-independent.

### 27.1 Value-object tests
**Test:**
*   unit conversion
*   coordinate validation
*   tolerance handling
*   angle normalization
*   positive dimension rules

### 27.2 Entity invariant tests
**Test:**
*   invalid room geometry
*   overlapping rooms
*   invalid walls
*   invalid openings
*   invalid staircase references
*   buildable-area violations
*   unsupported schema versions

### 27.3 Command tests
For every domain command, test:
*   valid operation
*   invalid operation
*   boundary conditions
*   resulting state
*   structured errors

### 27.4 Version tests
**Test:**
*   snapshot immutability
*   restore behavior
*   version numbering
*   revision conflicts
*   exact serialization/re-hydration

### 27.5 Property-based/fuzz tests
Where practical, generate random geometric inputs and assert:
*   no crashes
*   no NaN/Infinity propagation
*   invalid geometry is rejected
*   accepted geometry satisfies invariants

## 28. Non-Goals
The domain model does not attempt to represent:
*   structural engineering calculations
*   reinforcement design
*   legal land-survey certification
*   statutory approval workflows
*   construction-cost guarantees
*   construction-ready BIM semantics
*   arbitrary architectural curves in MVP
*   real-time multi-user collaborative editing in MVP

These may be introduced later as explicitly versioned domain extensions.

## 29. Future Extension Points
The domain should remain extensible for:
*   advanced sunlight/shadow analysis
*   richer site intelligence
*   additional layout strategies
*   more furniture libraries
*   additional AI providers
*   additional export formats such as DXF
*   advanced team permissions

## 30. Domain Model Open Questions
*   What exact MVP plot-boundary shapes should be supported: rectangle only, orthogonal polygon, or arbitrary simple polygon?
*   Should room geometry be stored as authoritative polygons, or should polygons always be derived from wall topology with rooms storing references/semantic boundaries?
*   What exact tolerance values should be used for canonical millimetre geometry and intersection detection?
*   Which hard constraints are product-mandated for MVP versus configurable project constraints?
*   What minimum door/window/staircase geometry rules are required in MVP before those elements are considered valid?
*   Should design analysis be stored as a versioned artifact, or recomputed from the canonical snapshot on demand with caching?
*   What exact share-link expiration defaults and approval/comment permissions should be configurable?
*   What plot/site inputs are required for MVP versus future site-intelligence analysis?

These decisions should be resolved before implementing the domain package and deterministic layout engine where they materially affect data structures or algorithms.

## 31. Implementation Boundary
The next implementation artifact after this document is the domain package design itself.

**Implementation should proceed in this order:**
1.  Define domain schemas and value objects.
2.  Define aggregate boundaries and invariants.
3.  Define canonical geometry primitives.
4.  Define domain commands and error codes.
5.  Add serialization/schema-version handling.
6.  Write invariant and command tests.

Only then implement the deterministic design engine against these stable domain contracts. No React component, Express route, Prisma model, Gemini integration, or 3D implementation should redefine these domain rules.
